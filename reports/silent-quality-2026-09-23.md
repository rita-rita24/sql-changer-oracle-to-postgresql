# 警告なしの誤変換を検出する検証

UI・CSS・固定文言・ボタンを維持し、変換ロジックと実DB差分検証を更新した。画面を除外した内部改善だけでは結果の同等性を保証できないため、元SQLをOracle、変換SQLをPostgreSQLで実行する検査を配布条件にした。

## 検証方法

既存345例に、直積・固定シードの生成例1,853件、別シードと入れ子・多行・0行・N文字列の463件、文字幅・動的引数の366件を追加した。合計3,027件。全列の型の分類も比較し、両方NULLや0行でも型の差を見逃さない。値・文字列の空白・NULL・行数・数値精度を保持して比較する。警告は不一致を合格にする理由にしない。

元SQLのエラーと変換後だけのエラーを区別する。新規の生成例には例外を設けない。従来からの4件の既知制約と11件の不正入力だけを別集計する。初期ジェネレータのOracleで無効なNULLIF例6件を除き、日付の負数演算がコメントになる8件の生成方法を修正した。初期記録も保存している。

追加シード17・99を使った中間検証では3,620件を実行し、予期しない不一致0件だった。この検証後にN文字列・日本語CHARの25件を追加し、副作用を修正した。最終ソースの検証結果は配布時の `database-comparison.json` と `validation.json` に記録する。

## 最終版の確認

- 追加シード17・99を含む最終版でも3,645件を実行し、結果同等3,630件、従来の既知制約4件、不正入力11件。予期しない不一致0件。既定の3,027件に加わった618件もすべて同等だった。
- 実DB: 3,027件。結果同等3,012件、以前からの既知制約4件、不正入力の拒否11件。予期しない不一致・警告なしの不一致・警告なしの実行エラー・元SQLの予期しないエラーはいずれも0件。
- 単体テスト233件、Chromium・Firefox・WebKitのE2E 207件、限定した変異テスト11件が成功。静的HTML・JavaScript構文検査も成功。
- PostgreSQL単独の27件も成功（修正確認26件、既知制約1件）。
- 静的HTML・CSS・固定文言は修正前と同一。ボタン数は4個のまま。
- `npm run release` が全必須検査を通過し、配布HTMLと検証対象HTMLの内容・SHA-256が一致した。

最終HTMLのSHA-256: `4f7dbfa194c86fdb0b94f2152c62deec7cc6a269b4c66ddeabe4fef221358b1d`。

性能の参考測定を `silent-performance-2026-09-23.json` に保存した。ローカル3回の測定では、同一文1,800件は中央値約23ms、異なる文1,000件は約383ms。後者は修正前約355msから増えた。意味の補正により出力SQLの長さも増える。端末全般での性能保証ではない。

## 検出と修正

最終と同じ3,027件を修正前の版（SHA-256 `55f0dea94391b313cc280569e4567f32b5f0778f4c539be00957db78905e546c`）で実行すると、予期しない失敗690件だった。警告なしの値・行の不一致460件、型だけの不一致19件、実行エラー149件を含む。元SQLの予期しないエラーは0件。記録は `semantic-baseline-2026-09-23.json`。

初回の有効な1,853例では、警告なしの値または型の不一致172件、警告なしの実行エラー97件を検出した。別に作成した438例では5件の警告なしの不一致があり、日本語の文字埋めを掘り下げた322例では246件が不一致だった。これらの数字は入力ケース数であり、独立した不具合の件数や任意のSQLの不良率ではない。

主な原因を修正した。

- 空文字・TRIM等の空結果がNULLにならず、条件式・集計・COALESCEの結果が変わる。
- REPLACEのNULL引数、NVL2の最初の結果、INSTRのNULL結果で値や戻り値の型が変わる。
- CHARをTEXTへ変換すると末尾空白が失われる。日本語CHARリテラルのバイト長とPostgreSQLの文字数も異なる。
- MODの除数0、文字列数値の算術、ROUND/TRUNCの小数桁、入れ子のDATE計算で結果や実行可否が変わる。
- LPAD/RPADの表示幅が文字数とは異なる。日本語・絵文字・半角文字・結合文字・埋め草の途中切断を実DBで比較し、動的引数を1回だけ評価する式で補正した。
- 新しい空文字補正が `N''` を壊す副作用と、AL16UTF16の国際文字列リテラルのLENGTHを追加検査で検出し修正した。

OracleのLPAD/RPADは表示幅を使うことが公式仕様にある。[Oracle LPAD](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/LPAD.html)、[Oracle RPAD](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/RPAD.html)。推測した幅表ではなく、検証用OracleでUnicodeの有効コードポイントを走査して得た757範囲を使用する。測定SQL・文字セット・範囲は `oracle-display-width-2026-09-23.json` に保存した。

## 再現と検証範囲

```sh
SQL_CHANGER_DOCKER_CONTEXT=colima-sql-changer-validation npm run release
SQL_CHANGER_DISCOVERY_SEEDS=17,99 SQL_CHANGER_DOCKER_CONTEXT=colima-sql-changer-validation npm run test:discovery
```

追加シードは固定の回帰集合を置き換えず、新しい式を追加する。ケースID・元SQL・変換SQL・Oracle結果・PostgreSQL結果・警告・型・分類・ソースと集合のSHA-256・DBイメージ・セッション設定を保存する。DB起動・比較・後片付けの失敗は成功扱いにしない。

Oracle 26ai Free 23.26.3、AL32UTF8/AL16UTF16、NLS_LENGTH_SEMANTICS=BYTE、固定した数値・日付設定とPostgreSQL 15.17での検証である。型は意図したNUMBER→NUMERIC、DATE→TIMESTAMPを許容する分類であり、宣言幅・宣言精度の完全比較ではない。任意のスキーマ、別の文字セット・照合順序・NLS設定、全Oracle構文での同等性を保証するものではない。LPAD/RPADの補助式は長くなるため、実データでの実行計画・処理時間も利用先で確認する。

検出力を確認するため、型だけ違うNULL結果、0行の型違い、数値と数値文字列、空文字とNULL、精度損失、警告付きの不一致を比較器の回帰テストに含めた。静的UIの同一性は `silent-ui-preservation-2026-09-23.json` に記録する。
